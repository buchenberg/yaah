`write(content, filePath)` - Creates a file. Replacing a file that already exists needs `overwrite: true`; for a partial change use `edit` or `patch` instead.

Writes are confined to the workspace root. Paths outside it (including the system temp directory) are refused with the rejected path and the allowed root; use `.scratch/` inside the workspace for disposable files.

`write` means "this path should hold exactly this content", and an existing path is usually a name collision rather than an intent - a new file whose name someone else already used. So a write to a path that already holds content is refused, nothing changes, and the error names the size and line count of what would have been lost plus the three ways out: pass `overwrite: true` if the replace is intended, use `edit`/`patch` for a partial change, or pick a different path.

An approved overwrite keeps the previous bytes: they are stashed inside the workspace at `.scratch/overwritten/` (bounded to the newest 100 entries) and the tool result names the stash path. That is the same confined world as the file itself, so for a sub-agent dispatch world the stash belongs to that world. A mistaken replace is then one copy away rather than a rewrite from memory. If the stash cannot be written the overwrite is refused - a replace that cannot be recovered is not worth performing.

`if_digest` makes a replace verified instead of blind: pass the sha256 of the content you expect to find, in the form the receipts print (`sha256:` plus a 12-character hex prefix) or a bare hex digest of at least 12 characters. The write is refused when the file differs, and the error names both digests; passing `if_digest` for a path that does not exist is refused too, so "replace what I read" and "create if absent" cannot be confused.

Writes to the same file are serialized in-process, so a same-file pair in one batch is ordered rather than lost - the later call simply wins, and its receipt's before-bytes show what it replaced. The guard's compare-and-swap additionally refuses a write when an out-of-band writer changed the file inside the call, with both digests (`file changed by another writer ...; re-read and retry`). A successful write ends with a receipt line - the path, the byte delta, and the digest of what is now on disk; `created` rather than `wrote` marks a file that did not exist before the call.
